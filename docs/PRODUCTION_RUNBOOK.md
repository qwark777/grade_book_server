# Production runbook

## Required checks before deploy

Run these commands from `grade_book_server`:

```bash
python3 scripts/generate_production_env.py \
  --domain gradebook.your-domain.ru \
  --api-domain api.gradebook.your-domain.ru
bash scripts/predeploy_check.sh
```

Or run the combined local predeploy check:

```bash
bash scripts/predeploy_check.sh
```

`scripts/doctor.py` must run with the same environment variables that will be used by the server.
Fix every `[ERROR]` before starting the app. Treat `[WARN]` items as release blockers for public
production unless there is a documented reason.

## Required environment

- `SECRET_KEY`: long random value, not a development default.
- `ENCRYPTION_KEY`: Fernet key generated by `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`.
- `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DB`: database connection.
- `APP_HOST=0.0.0.0` only inside Docker or behind a trusted reverse proxy. Local direct runs should keep `127.0.0.1`.
- `BACKEND_CORS_ORIGINS`: comma-separated frontend origins, for example `https://school.example.com`.
- `TRUSTED_HOSTS`: comma-separated API hostnames accepted by the backend.
- `ALLOW_INSECURE_DEV_DEFAULTS` must not be enabled in production.

## Docker production deploy

Use the production compose file for public deployments. Start the database,
apply migrations in a one-off app container, and only then start the API:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production up -d db
docker compose -f docker-compose.prod.yml --env-file .env.production run --rm app python -m alembic upgrade head
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build app
docker compose -f docker-compose.prod.yml --env-file .env.production ps
```

The production compose file:

- Uses a dedicated MySQL user for the app.
- Does not publish MySQL to the host network.
- Publishes the API only on `127.0.0.1:${APP_PORT:-8001}` for a local reverse proxy.
- Persists database data and every uploaded-file directory in Docker volumes.
- Checks `/api/v1/health` at container level.

## Migrations

The baseline migration bootstraps missing core tables and all later migrations
are idempotent. Use the same command for a new database and an existing
pre-Alembic database:

```bash
python -m alembic upgrade head
```

When using Docker, run migrations inside the app container:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production exec app python -m alembic upgrade head
```

## Health and logs

- Health endpoint: `GET /api/v1/health`.
- Every HTTP response includes `X-Request-ID` and `X-Process-Time`.
- Clients or proxies may send `X-Request-ID`; otherwise the API generates one.
- Use the request id when correlating app logs, proxy logs, and user support reports.

After deploy:

```bash
curl -fsS https://school.example.com/api/v1/health
docker compose -f docker-compose.prod.yml --env-file .env.production logs --tail=100 app
```

## Reverse proxy

Use `deploy/nginx/gradebook.conf` as the nginx starting point. Replace:

- `school.example.com`
- `api.school.example.com`
- certificate paths under `/etc/letsencrypt/live/...`

The app container binds to localhost, so nginx should proxy to `http://127.0.0.1:8001`.
The template includes WebSocket upgrade headers for `/ws` and passes `X-Request-ID`.

## Backup and restore

Create a backup:

```bash
COMPOSE_FILE=docker-compose.prod.yml BACKUP_DIR=backups bash scripts/backup.sh
```

The backup includes:

- MySQL dump: `backups/gradebook_<timestamp>.sql.gz`
- Uploaded files: `backups/gradebook_<timestamp>_files.tar.gz`
- Manifest with checksums: `backups/gradebook_<timestamp>.manifest`

Restore requires an explicit confirmation variable because it overwrites database and uploaded files:

```bash
CONFIRM_RESTORE=yes COMPOSE_FILE=docker-compose.prod.yml \
  bash scripts/restore.sh backups/gradebook_YYYYMMDDTHHMMSSZ
```

Test restore on staging before relying on a backup procedure in production.

## Security gates

`scripts/security_check.sh` runs:

- Python compile checks.
- Role/access and upload security tests.
- `pip-audit` for known dependency vulnerabilities.
- Semgrep security rules, including new untracked files under `app/`.
- Bandit for medium/high confidence issues.
- Search for forbidden insecure patterns such as query-string tokens and weak defaults.
